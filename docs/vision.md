# Vision: API-витрина МойСклад

## Идея

Сервис — это REST-обёртка над JSON API МойСклад (Remap 1.2), которая повторяет
покупательский сценарий витрины «Онлайн-заказ»: показать каталог так, как он настроен
в МойСклад, собрать корзину, проверить наличие и оформить заказ. Собственной БД нет:
товары, цены и остатки — источник истины МойСклад; единственное локальное состояние —
файл корзины `data/cart.json` (MVP Sprint 7).

## Полный пользовательский сценарий (end-to-end)

1. **Каталог** — клиент получает товары витрины с ценами и остатками:
   `GET /api/products` (с настройками отображения, пагинацией и фильтрами).
2. **Корзина** — клиент добавляет, смотрит и удаляет позиции:
   `POST /api/cart/items`, `GET /api/cart`, `DELETE /api/cart/items/{id}`.
   Корзина хранится в файле и переживает перезапуск приложения.
3. **Проверка перед заказом** — клиент передаёт позиции и количество:
   `POST /api/orders/validate`; сервис отвечает `valid` и структурированными ошибками
   с альтернативами. Заказ на этом шаге не создаётся.
4. **Создание заказа** (после Sprint 7) — если позиции доступны, сервис создаёт заказ
   покупателя в МойСклад: `POST /api/orders`.
5. **Чтение заказа** (после Sprint 7) — клиент проверяет результат по идентификатору:
   `GET /api/orders/{id}` (состав, количество, суммы, статус).

Это целевой сценарий проекта целиком: от просмотра витрины до подтверждённого заказа
в учебном аккаунте МойСклад.

## Границы по этапам

- **Sprint 5 (готово):** витрина и её настройки — каталог, options/config,
  пагинация, фильтрация, витринная логика «Онлайн-заказ».
- **Sprint 6 (готово):** полный каталог постранично, кеши ассортимента и остатков,
  текущий отчёт об остатках, сквозные тесты и документация.
- **Sprint 7 (текущий):** delta-синхронизация остатков, файловая корзина MVP,
  pre-order validation без создания заказа.
- **После Sprint 7:** реальное создание и чтение заказа в МойСклад.
- **P1:** MCP-интерфейс — те же возможности (каталог, корзина, остатки, проверка,
  заказы) в виде инструментов для AI-агентов. Инструменты заказов — после Sprint 8.

## MCP-интерфейс (future, P1)

В рамках P1 те же возможности сервиса станут доступны AI-агентам через MCP: инструменты
каталога, корзины и проверки — после Sprint 7, инструменты заказов — после Sprint 8.
MCP-слой — тонкая обёртка над существующими сервисами, а не второй набор бизнес-логики:
REST и MCP должны возвращать одинаковые данные и одинаковые ошибки.

### Планируемые инструменты

| Инструмент | Что делает | REST-эквивалент | Когда |
|---|---|---|---|
| `catalog_list` | постраничный каталог с фильтрами и настройками витрины | `GET /api/products` | P1, после Sprint 7 |
| `catalog_config` | доступные типы цен, группы и поля | `GET /api/products/config` | P1, после Sprint 7 |
| `availability_check` | проверка остатков по позициям | `POST /api/availability` | P1, после Sprint 7 |
| `cart_get` | состав файловой корзины | `GET /api/cart` | P1, после Sprint 7 |
| `cart_add_item` | добавить товар в корзину | `POST /api/cart/items` | P1, после Sprint 7 |
| `cart_remove_item` | удалить товар из корзины | `DELETE /api/cart/items/{id}` | P1, после Sprint 7 |
| `order_validate` | проверка перед заказом с альтернативами | `POST /api/orders/validate` | P1, после Sprint 7 |
| `order_create` | создать заказ покупателя | `POST /api/orders` | P1, после Sprint 8 |
| `order_get` | прочитать заказ по id | `GET /api/orders/{id}` | P1, после Sprint 8 |

### Правила реализации

- MCP-инструменты вызывают те же сервисы, что и контроллеры (`ProductService`,
  `CartService`, `AvailabilityService`, `OrderValidationService`); дублирования
  бизнес-логики нет.
- Входы, выходы и коды ошибок совпадают с REST; ошибки MCP повторяют `ErrorResponse`.
- Инструменты, меняющие состояние (`cart_*`, `order_create`), явно описывают побочные
  эффекты. Повторное добавление товара увеличивает количество — как в REST.
- Токен МойСклад и содержимое `.env` никогда не попадают в ответы инструментов и логи.
- MCP использует те же кеши ассортимента и остатков и не создаёт дополнительную
  нагрузку на Remap.

### Критерий готовности MCP

Один и тот же сценарий (каталог → корзина → проверка → заказ → чтение заказа)
воспроизводится и через REST, и через MCP на учебном аккаунте МойСклад; ответы
инструментов совпадают с REST для тех же запросов.

## Принципы

- **Тонкие контроллеры**: валидация входа и делегирование в сервисы.
- **Функциональный Java 21**: records, Streams, `Optional`, method references.
- **Деньги — только `BigDecimal`**: разбор из строки, сравнение через `compareTo`,
  арифметика через `add`/`multiply`/`divide` с `RoundingMode`.
- **Понятные ошибки**: структурированный `ErrorResponse`, корректные HTTP-статусы,
  без стектрейсов наружу.
- **Разделение DTO**: Remap-модели (`...RemapDto`) не выходят за слой клиента/маппера.
- **Никаких секретов в репозитории**: токен только из окружения / `.env`.

## Out of Scope (для проекта в целом)

- Собственная БД сервиса: товары, цены и остатки — только из МойСклад; корзина —
  файловый MVP (`data/cart.json`), а не БД.
- Платёжный сценарий и оформление оплаты.
- Авторизация покупателей и персональные цены контрагентов.
- Административный интерфейс и произвольная запись данных в МойСклад.

## Критерий успеха проекта

Полный end-to-end сценарий на `curl` и Swagger UI:
настроить витрину → получить постраничный отфильтрованный каталог → собрать корзину →
проверить заказ → создать заказ → прочитать созданный заказ. Плюс те же операции
через MCP-инструменты после реализации заказов. Всё — на реальных данных учебного МойСклад.
