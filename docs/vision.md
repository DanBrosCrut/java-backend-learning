# Vision: API-витрина МойСклад

## Идея

Сервис — это REST-обёртка над JSON API МойСклад (Remap 1.2), которая повторяет
покупательский сценарий витрины «Онлайн-заказ»: показать каталог так, как он настроен
в МойСклад, проверить наличие и оформить заказ. Собственной БД нет, **backend полностью
stateless**: товары, цены и остатки — источник истины МойСклад, а корзина на сервере не
хранится.

## Архитектура: agent-owned cart

- Backend не хранит состояние между запросами: нет корзины, нет файлов, нет сессий.
- **Корзину ведёт AI-агент (или MCP-клиент)** в собственном контексте между ходами
  диалога: он запоминает выбранные позиции (`productId` + `quantity`).
- В API корзина передаётся только как полный список позиций — для валидации
  (`POST /api/orders/validate`) и создания заказа (`POST /api/orders`).
- Все запросы на чтение идемпотентны; единственный побочный эффект — реальный заказ,
  создаваемый `POST /api/orders`.

## Полный пользовательский сценарий (end-to-end)

1. **Каталог** — клиент/агент получает товары витрины с ценами и остатками:
   `GET /api/products` (с настройками отображения, пагинацией и фильтрами).
2. **Корзина у агента** — агент накапливает позиции в своём контексте между ходами;
   сервер о корзине ничего не знает и ничего не сохраняет.
3. **Проверка перед заказом** — агент передаёт позиции и количество:
   `POST /api/orders/validate`; сервис отвечает `valid` и структурированными ошибками
   с альтернативами. Заказ на этом шаге не создаётся.
4. **Создание заказа** — если позиции доступны, сервис создаёт заказ покупателя
   в МойСклад: `POST /api/orders` (Sprint 8). При нехватке остатка — `409`, заказ
   не создаётся.
5. **Чтение заказа** — клиент проверяет результат по идентификатору:
   `GET /api/orders/{id}` (состав, количество, суммы, статус; Sprint 8, далее).

Это целевой сценарий проекта целиком: от просмотра витрины до подтверждённого заказа
в учебном аккаунте МойСклад.

## Границы по этапам

- **Sprint 5 (готово):** витрина и её настройки — каталог, options/config,
  пагинация, фильтрация, витринная логика «Онлайн-заказ».
- **Sprint 6 (готово):** полный каталог постранично, кеши ассортимента и остатков,
  текущий отчёт об остатках, сквозные тесты и документация.
- **Sprint 7 (готово):** delta-синхронизация остатков, pre-order validation без
  создания заказа. Файловая корзина была MVP Sprint 7 и **удалена в Sprint 8**
  в пользу agent-owned cart.
- **Sprint 8 (текущий):** создание заказа, stateless backend (agent-owned cart),
  отдельный MCP-сервер.
- **P1:** MCP-интерфейс — те же возможности (каталог, остатки, проверка, заказы)
  в виде инструментов для AI-агентов.

## MCP-интерфейс

MCP-сервер — **отдельное приложение** в каталоге `mcp-server/`, а не часть Spring Boot
API: он ходит по HTTP в наш REST (`http://localhost:8080/api/...`) и не содержит
бизнес-логики. REST и MCP возвращают одинаковые данные и одинаковые ошибки.

### Планируемые инструменты

| Инструмент | Что делает | REST-эквивалент | Когда |
|---|---|---|---|
| `catalog_list` | постраничный каталог с фильтрами и настройками витрины | `GET /api/products` | Sprint 8 / P1 |
| `catalog_config` | доступные типы цен, группы и поля | `GET /api/products/config` | Sprint 8 / P1 |
| `availability_check` | проверка остатков по позициям | `POST /api/availability` | Sprint 8 / P1 |
| `order_validate` | проверка перед заказом с альтернативами | `POST /api/orders/validate` | Sprint 8 / P1 |
| `order_create` | создать заказ покупателя из позиций | `POST /api/orders` | Sprint 8 / P1 |
| `order_get` | прочитать заказ по id | `GET /api/orders/{id}` | после Sprint 8 |

Корзина — **не инструмент MCP**: агент держит позиции в собственном контексте между
ходами и передаёт их в `order_validate`/`order_create` списком.

### Правила реализации

- MCP-инструменты — тонкие HTTP-обёртки над REST; дублирования бизнес-логики нет.
- Входы, выходы и коды ошибок совпадают с REST; ошибки MCP повторяют `ErrorResponse`.
- Инструменты, меняющие состояние (`order_create`), явно описывают побочные эффекты
  (создание заказа в МойСклад).
- Токен МойСклад и содержимое `.env` никогда не попадают в ответы инструментов и логи.
- MCP работает через REST и потому использует те же кеши ассортимента и остатков.

### Критерий готовности MCP

Один и тот же сценарий (каталог → корзина в контексте агента → проверка → заказ →
чтение заказа) воспроизводится и через REST, и через MCP на учебном аккаунте МойСклад;
ответы инструментов совпадают с REST для тех же запросов.

## Принципы

- **Stateless backend**: никакого состояния на сервере; корзина — контекст агента.
- **Тонкие контроллеры**: валидация входа и делегирование в сервисы.
- **Функциональный Java 21**: records, Streams, `Optional`, method references.
- **Деньги — только `BigDecimal`**: разбор из строки, сравнение через `compareTo`,
  арифметика через `add`/`multiply`/`divide` с `RoundingMode`.
- **Понятные ошибки**: структурированный `ErrorResponse`, корректные HTTP-статусы,
  без стектрейсов наружу.
- **Разделение DTO**: Remap-модели (`...RemapDto`) не выходят за слой клиента/маппера.
- **Никаких секретов в репозитории**: токен только из окружения / `.env`.

## Out of Scope (для проекта в целом)

- Собственная БД сервиса: товары, цены и остатки — только из МойСклад.
- Хранение корзины на сервере (файловое или в БД): корзина — контекст агента.
- Платёжный сценарий и оформление оплаты.
- Авторизация покупателей и персональные цены контрагентов.
- Административный интерфейс и произвольная запись данных в МойСклад.

## Критерий успеха проекта

Полный end-to-end сценарий на `curl` и Swagger UI:
настроить витрину → получить постраничный отфильтрованный каталог → агент собирает
позиции в своём контексте → проверить заказ → создать заказ → прочитать созданный
заказ. Плюс те же операции через MCP-инструменты. Всё — на реальных данных учебного
МойСклад.
