# Product Backlog

Формат элемента: **что сделать · зачем · готово, если**

Собственной БД нет: товары, цены и остатки приходят из МойСклад. Backend полностью
**stateless**: корзину ведёт AI-агент (или MCP-клиент) в своём контексте между ходами
диалога и передаёт в API полный список позиций только для валидации и создания заказа.
Файловая корзина `data/cart.json` (MVP Sprint 7) удалена в Sprint 8. Полный целевой
сценарий проекта: каталог → корзина у агента → проверка перед заказом → создание
заказа → чтение заказа, затем MCP-интерфейс (см. `docs/vision.md`).

## P1 — Sprint 8: заказы и stateless backend

### Создать заказ покупателя
- **Что:** `POST /api/orders`: создание заказа из позиций запроса после проверки остатков.
- **Зачем:** завершение сценария покупки.
- **Готово, если:** заказ создан в учебном МойСклад; при нехватке остатка — отказ
  без создания заказа и структурированный `ErrorResponse`.
- **Статус:** реализовано, PR #106 (в ревью).

### Stateless backend: agent-owned cart
- **Что:** удалить файловую корзину; заказ принимает полный список позиций от клиента;
  корзину ведёт агент между ходами.
- **Зачем:** API без состояния на сервере, проще масштабирование и MCP-сценарии.
- **Готово, если:** эндпоинтов `/api/cart*` нет, позиции приходят в `POST /api/orders`,
  `data/cart.json` не используется.
- **Статус:** реализовано, PR #106 (в ревью).

### Прочитать заказ
- **Что:** `GET /api/orders/{id}`: состав, количества, суммы, статус.
- **Зачем:** проверить результат оформления.
- **Готово, если:** REST отдаёт заказ из МойСклад; неизвестный id → `404`.
- **Статус:** не начато.

## P1 — MCP-интерфейс

### MCP: каталог и остатки
- **Что:** `catalog_list`, `catalog_config`, `availability_check`.
- **Зачем:** витрина и остатки доступны AI-агентам.
- **Готово, если:** инструменты возвращают те же данные, что REST, и используют
  те же кеши.

### MCP: проверка заказа
- **Что:** `order_validate`; корзина — контекст агента, инструментов `cart_*` нет.
- **Зачем:** агент проверяет заказ до оформления, передавая позиции списком.
- **Готово, если:** структурированные ошибки совпадают с REST.

### MCP: отдельный сервер
- **Что:** приложение `mcp-server/` вне Spring Boot API; HTTP-обёртка над REST
  (`http://localhost:8080/api/...`), без бизнес-логики; README по запуску.
- **Зачем:** MCP-интерфейс не смешивается с REST-кодом.
- **Готово, если:** инструменты каталога и заказов работают через HTTP, ошибки
  повторяют `ErrorResponse`.

### MCP: заказы
- **Что:** `order_create`, `order_get` после реализации реальных заказов.
- **Зачем:** полный сценарий покупки через агента.
- **Готово, если:** сценарий воспроизводится через MCP на учебном аккаунте.

### MCP: единый контракт
- **Что:** общие DTO и коды ошибок для REST и MCP, описание побочных эффектов,
  запрет на токены в ответах инструментов.
- **Зачем:** предсказуемое поведение и безопасность.
- **Готово, если:** контрактные тесты MCP и REST проходят на одних и тех же запросах.
