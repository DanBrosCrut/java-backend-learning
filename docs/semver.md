# Semantic Versioning (SemVer)

Проект использует [Semantic Versioning 2.0.0](https://semver.org/). Формат версии:
MAJOR.MINOR.PATCH

text

## Что означает каждая часть

| Часть | Когда увеличивается | Пример |
|-------|---------------------|--------|
| **MAJOR** | Ломающие изменения API (несовместимые) | `1.5.2 → 2.0.0` |
| **MINOR** | Новая функциональность с обратной совместимостью | `1.5.2 → 1.6.0` |
| **PATCH** | Исправление багов с обратной совместимостью | `1.5.2 → 1.5.3` |

## Правила

- **MAJOR = 0** — проект в активной разработке, API может меняться без предупреждения.
- После первого стабильного релиза — `1.0.0`.
- При увеличении MAJOR — MINOR и PATCH сбрасываются в 0.
- При увеличении MINOR — PATCH сбрасывается в 0.

## Текущая версия проекта

**`0.2.0`**

История:
- `0.1.0` — старт проекта, `GET /health` (спринт 1)
- `0.2.0` — добавлен `GET /api/products` (спринт 2)

## Пример на своём изменении

**Изменение:** добавлен новый эндпоинт `GET /api/products`, возвращающий каталог товаров из МойСклад.

**Тип bump:** **MINOR** (`0.1.0 → 0.2.0`)

**Почему:**
- Это **новый функционал** — раньше эндпоинта не было.
- Он **обратно совместим** — `GET /health` продолжает работать как раньше, ничего не сломано.
- Существующие клиенты ничего не потеряли.

**Почему не MAJOR:** нет ломающих изменений — старый эндпоинт `/health` работает.
**Почему не PATCH:** это не багфикс, а именно новая функциональность.

## Как ставить тег

```bash
git checkout main
git pull
git tag -a v0.2.0 -m "Sprint 2: GET /api/products endpoint"
git push origin v0.2.0
```
Release на GitHub
После тега — создать Release:
Репозиторий → Releases → Create a new release
Выбрать тег v0.2.0
Написать release notes (что нового, какие Issues закрыты)
Publish

Версии в pom.xml
Версия проекта в pom.xml должна соответствовать SemVer:

```xml
<version>0.2.0</version>
```
При следующем изменении — увеличивать соответственно: MINOR для новых фич, PATCH для багфиксов.
